Build, CI, and packaging#

G1 — portal/Dockerfile is missing 🔴#

docker-compose.yml declares portal: build: ./portal, but no Dockerfile exists there (gateway/Dockerfile does). docker compose up fails while building the portal service.

Fix. Add a portal Dockerfile — a Vite build plus a static server or nginx stage.

G2 — The gateway image builds nothing to run 🔴#

gateway/Dockerfile runs RUN npx tsc in the builder stage, copies /app/dist, and starts CMD ["node", "dist/index.js"]. But gateway/tsconfig.json sets "noEmit": true, so tsc type-checks and emits no files. Verified: npx tsc produces no dist/ directory, and package.json has no build script.

Effect. The image either fails to build at the COPY --from=builder /app/dist step, or starts and immediately exits on a missing entry point. There is no working container today.

Fix. Add an emitting build config (tsconfig.build.json with noEmit: false and an outDir) and a build script — or run tsx src/index.ts in the container, matching the supported local path.

G3 — Lint fails, so CI is red 🔴#

ESLint 9.39.5 is installed, but the config is gateway/.eslintrc.json — the v8 format. Running npm run lint produces:

ESLint couldn't find an eslint.config.(js|mjs|cjs) file.
From ESLint v9.0.0, the default configuration file is now eslint.config.js.

.github/workflows/ci.yml runs npm run lint as a required step, so every push and pull request fails CI regardless of code quality — which means CI gates nothing.

Fix. Migrate to flat config (eslint.config.js), or pin ESLint 8.

G20 — The CI self-test is a no-op 🟡#

The workflow's "Self-test" step uses CommonJS require('./dist/service.js') in a package declared "type": "module", against a dist/ that is never built (see G2) — and the whole step ends in || echo "Self-test completed", so it reports success unconditionally.

Fix. Drop it, or rewrite it as a Vitest integration test where failures actually fail.

Correctness#

G13 — Every user-compiled bundle contains a failing test, blocking publish 🔴#

The highest-impact defect in the product.

buildTests() derives an expectation from the IAC_SAMPLES key: anything not ending in -good expects deny. IAC_SAMPLES includes cfn-good and cfn-bad. But no control template in kb.ts declares a cloudformation static target (grep -c 'provider: "cloudformation"' src/kb.ts → 0), so no compiled policy can produce a CloudFormation violation.

Verified against the persisted seed bundle:

bundle v1 | Baseline: GDPR + SOC 2 | consistency: 100
tests: 14 passed: 13
  FAIL: t-cfn-bad | CloudFormation template — insecure stack (violations)
        | expect deny | builtin allow | opa allow

Both engines agree — so semantic consistency reads 100% — but they agree on the wrong answer, and the expectation catches it.

Effect. POST /api/prs/:id/publish refuses to publish while any test fails:

const failed = bundle.testResults.filter((t) => !t.passed).length;
if (failed > 0) return res.status(400).json({ error: `${failed} policy test(s) failing; cannot publish` });

Every bundle a user compiles inherits t-cfn-bad, so the publish path is blocked. The seeded baseline is unaffected only because seed() sets activeBundleId directly, bypassing the guard. A user who ingests a document, approves controls, and compiles cannot ship the result.

Fix. Add at least one kb.ts template with a cloudformation static target (and the compile.ts branch from G12), or remove the cfn-* fixtures from IAC_SAMPLES until CloudFormation is supported end to end.

G12 — CloudFormation compiles to Rego that can never match 🟠#

staticRule() in compile.ts branches only on provider === "terraform" and treats everything else as Kubernetes:

const providerGuard = isTf ? `input.iac_provider == "terraform"`
                           : `input.iac_provider == "kubernetes"`;
const iter        = isTf ? `rc := input.resource_changes[_]` : `m := input.items[_]`;

A cloudformation static target therefore compiles into a rule guarded by input.iac_provider == "kubernetes" that iterates input.items[_]. Against a real CloudFormation template it never fires.

evalStaticBuiltin() in engine.ts, by contrast, has a correct CloudFormation branch reading Resources and Properties.

Effect. Once any CloudFormation control exists, the two engines disagree: OPA passes everything, the builtin evaluator enforces. Because OPA is preferred, real-world scanning would silently allow non-compliant templates.

Fix. Add a CloudFormation branch to staticRule() mirroring the builtin evaluator.

G7 — The CLI's --state flag has no effect 🟠#

cli.ts documents --state <path> and checks that the file exists, then calls getState(seed) — which reads <cwd>/<DATA_DIR>/grcstudio.db regardless. The comment beside the check still refers to data/state.json, from before the SQLite migration.

Effect. A pipeline that passes --state gets a false sense of having pointed the scanner somewhere; it silently scans against whatever database is in the working directory, or fails with "no published policy bundle".

Fix. Honour the flag by overriding the database path, or remove it and document Pattern 2 (the OPA bundle) for remote pipelines.

G11 — The test suite is not isolated 🟡#

opaEval() writes to fixed paths — data/opa-tmp/policy.rego and data/opa-tmp/input.json — then invokes the OPA binary against them. Vitest runs test files in parallel worker processes, so two files evaluating simultaneously can overwrite each other's fixtures.

Observed once: a full npm test run failed service.test.ts > should mark builtin result for each test, and passed on every subsequent run, when run alone (10/10), and under --poolOptions.forks.singleFork (87/87).

Effect. Intermittent CI failures with no code change. Within a single process the risk is absent — writeFileSync/execFileSync cannot interleave — so this is a cross-process issue: parallel test workers, or multiple gateway instances sharing a working directory.

Fix. Use a unique temp directory per evaluation (mkdtempSync), which also removes the multi-instance hazard.

Security#

G14 — Open registration with a caller-chosen role 🔴#

POST /api/auth/register is on the auth router, which index.ts mounts before app.use("/api/", requireAuth). It is therefore reachable without any credential, in every mode including production. The handler accepts a role from the request body:

const validRoles = ["compliance", "security", "aiops", "admin"];
const userRole = validRoles.includes(role) ? role : "compliance";

admin is in the list. The source comment above the route claims *"In production, requires admin token"* — no such check exists.

Effect. Anyone who can reach the gateway can create an admin account:

curl -X POST https://host/api/auth/register -H 'Content-Type: application/json' \
  -d '{"email":"x@x.com","password":"…","name":"x","role":"admin"}'

An admin can grant waivers (disabling controls) and, per G10, single-handedly satisfy two-person approval and publish a bundle.

Fix. Move registration behind the auth middleware and require admin, or ignore caller-supplied role and default to compliance.

G5 — seed-passwords is unauthenticated and returns the password 🔴#

POST /api/auth/seed-passwords, also on the pre-auth router, finds every user with a NULL passwordHash, sets them all to config.defaultPassword (default grcstudio123), and returns it:

res.json({ seeded: usersWithout.length, users: …,
           defaultPassword: config.defaultPassword,
           message: `Default password set to "${config.defaultPassword}" …` });

The source comment claims "Only works in dev mode" — there is no config.isProd or authEnabled guard in the handler.

The three seeded users are inserted without password hashes (INSERT INTO users (id, name, role)), so on a fresh deployment Priya (compliance), Sam (security) and Ava (aiops) all qualify.

Effect. On a fresh production deployment, whoever calls this endpoint first obtains working credentials for all three — including the security role that grants waivers and approves compliance PRs. Once passwords exist the endpoint becomes inert, so the exposure is the window between first boot and provisioning — not a window you control on an internet-facing service.

Fix. Guard it with config.isProd, move it behind auth, stop returning the password, or delete it and provision passwords out of band.

G4 — Dev mode has no authentication 🔴#

When AUTH_ENABLED is not true (the default outside NODE_ENV=production), requireAuth falls back to the X-GRC-User header:

const userId = req.header("X-GRC-User") ?? "u-priya";
req.authUser = { userId, role: "compliance" };   // role hard-coded

Any caller can claim any user id. req.authUser.role is hard-coded to compliance regardless of who the header names — which is why routes that enforce roles correctly re-resolve the user from the database instead.

The exported requireRole middleware returns next() without checking anything in dev mode; it is currently used by no route.

Effect. Anything not explicitly running with auth enabled is fully open. The role checks that do exist are only as trustworthy as the identity behind them.

Fix. Make AUTH_ENABLED=false an explicit opt-in rather than a default, and log a loud warning at startup when auth is off and the bind address is not loopback.

G10 — One admin satisfies two-person approval 🟠#

if (user.role === "security" || user.role === "admin") pr.approvals.security ??= {…};
if (user.role === "aiops"    || user.role === "admin") pr.approvals.aiops    ??= {…};

A single admin call fills both slots, so the separation-of-duties control that distinguishes the product can be satisfied by one identity.

Related: POST /api/prs/:id/publish and /reject carry no role check at all — any caller can publish once approvals exist, or reject an open PR outright.

Fix. Require two distinct user ids regardless of role, and role-gate publish and reject.

G9 — No service accounts; JWT_SECRET defaults to random 🟠#

Two related integration problems:

  1. There is no API-key or service-account credential type. CI pipelines and agent runtimes must authenticate as a human user with a 24-hour token, and there is no revocation.
  2. config.jwtSecret falls back to randomBytes(32) generated per process. Tokens do not survive a restart and are invalid across replicas unless JWT_SECRET is set explicitly.

Fix. Require JWT_SECRET in production (fail fast when unset), and add a scoped service-credential type.

G19 — The audit chain is tamper-evident, not tamper-proof 🟡#

Each entry stores SHA-256(id + at + user + action + detail + prevHash) and GET /api/audit/verify reports the first broken index. That defeats casual row editing.

It does not defeat an attacker with write access: they can recompute the chain forward from the row they changed. There is no external anchoring, no signature over the head, and the chain covers only the most recent AUDIT_MAX_ENTRIES rows loaded into state.

Fix. Periodically publish the head hash somewhere append-only, or sign it.

G21 — The error handler echoes exception messages 🟡#

res.status(500).json({ error: err.message || "Internal server error" });

Unhandled errors return their message to the client, which can disclose file paths, SQL fragments, or upstream detail.

Fix. Return a generic message plus a correlation id in production; log the detail.

G22 — Single-tenant, with unrestricted read access 🟡#

One organisation per deployment; roles scope permissions, not data. And no read endpoint is role-gated — any authenticated caller (in dev mode, anyone) can read every control, every bundle's full Rego, all decisions and scans, the waiver register, the audit log, and the complete evidence export.

Fix. Gate reads by role where the data is sensitive; add a tenant dimension if multi-tenancy is ever required.

Architecture and scale#

G6 — Single writer, and OPA CLI blocks the event loop 🟠#

Two constraints from the same design choice.

Whole-state persistence. state() materialises every table into one State object; handlers mutate it; save() writes it all back. Two gateway processes against one SQLite file will overwrite each other's changes. Run exactly one instance.

Synchronous OPA. opaEval() uses execFileSync with a 10-second timeout — it spawns a process and blocks the Node event loop for the whole evaluation. Concurrent scans and authorizations serialise behind it. Since authorize is on the hot path of every agent tool call, this caps throughput.

Fix. Set OPA_SERVER_URL to use the async HTTP path against a persistent OPA server — opaServerEval() already exists. For horizontal scale, the state model needs incremental writes.

G15 — Bounded histories are deleted, not just unloaded 🟠#

save() runs DELETE FROM decisions, DELETE FROM scans, and DELETE FROM audit, then reinserts what is in memory — and loadState() only loaded the most recent DECISION_MAX_ENTRIES (200), SCAN_MAX_ENTRIES (100), and AUDIT_MAX_ENTRIES (300).

Effect. Older rows are permanently removed from the database on the next save, not merely omitted from the working set. An operator who assumes SQLite retains full history — and that raising the limit later will surface it — will find it gone. For audit evidence in particular, this is a retention trap.

Fix. Load bounded windows for display but persist incrementally, or document the trim explicitly in the UI and raise the defaults.

G8 — Webhook registrations are in memory 🟠#

webhooks.ts holds registrations in a module-level array with the comment *"can be persisted via settings later"*. POST /api/webhooks survives only until the process restarts.

Delivery is also fire-and-forget with a 10-second timeout and no retry — a failed notification is logged and lost.

Fix. Add a webhooks table, and a retry queue if delivery matters.

G16 — The Policy Gateway is a decision point, not an interceptor 🟠#

POST /api/gateway/authorize returns a verdict. Nothing intercepts tool execution. An agent that never calls it is never governed.

This is a reasonable architecture — it works with any agent framework and needs no SDK — but it moves the enforcement guarantee into the customer's agent runtime. Any bypass, deliberate or accidental, is invisible to GRCStudio.

Fix (customer side). Put the authorize call in the single code path every tool executes through, and treat bypassing it as a build failure. Fix (product side). Ship a wrapper SDK or a proxy mode so enforcement is structural rather than conventional.

Coverage and content#

G17 — 18 control templates is a baseline, not coverage 🟠#

The deterministic knowledge base holds 18 templates across seven frameworks: 4 SOC 2, 3 GDPR, 3 NIST CSF, and 2 each for CCPA, ISO 27001, HIPAA, and PCI DSS.

Extraction is keyword matching — a document citing an article with no matching template produces nothing at all, silently. Cross-framework mapping covers six concepts, not whole frameworks.

Effect. Without an Anthropic API key, the platform can only recognise what its templates already know. That is fine for a demonstration and insufficient for real compliance breadth.

Fix. Treat Claude extraction as required rather than optional for real use, and expand the knowledge base for the frameworks you actually sell against.

G18 — PII detection is a three-pattern regex 🟡#

PII_PATTERN covers US SSN (ddd-dd-dddd), a 13–16-digit payment card, and email addresses.

It will not catch names, postal addresses, phone numbers, passport or national ID numbers, dates of birth, medical record numbers, free-text disclosure, or any obfuscated value.

Effect. pii_egress is a tripwire for formatted identifiers, not a data-classification control. Do not present it as PHI/PII protection.

Fix. Pluggable detectors, or an LLM classification pass for high-risk flows.

Documentation and hygiene#

G23 — Source comments describe protections that do not exist ⚪#

Two comments in routes/auth.ts assert security properties the code does not implement:

CommentReality
"In production, requires admin token" (register)No check — see G14
"Only works in dev mode" (seed-passwords)No check — see G5

A reviewer skimming for security issues would read these and move on. That is worse than no comment.

Fix. Implement the guards, or delete the claims.

G24 — The in-repo API reference is stale ⚪#

README.md and docs/02-api-reference.md describe "all 42 endpoints". The source now defines 61. The in-repo docs predate roughly 19 routes, including the auth module.

Fix. Regenerate from source, as this documentation set does.
