Method#

Written from the source, not from the existing in-repo documentation. Where the two disagreed, the code won and the discrepancy was recorded.

Read in full

  • src/index.ts — middleware order, router mounting, and the auth boundary
  • src/types.ts — the entire domain model
  • src/compile.ts and src/engine.ts — the compiler and the builtin evaluator, side by side
  • src/service.ts — orchestration, dual-engine evaluation, waiver filtering, seeding
  • src/opa.ts — discovery, CLI evaluation, server mode
  • src/store.ts and src/db.ts — persistence, the audit hash chain, the schema
  • All seven route modules and middleware/requireAuth.ts
  • src/kb.ts, src/samples.ts, src/crossmap.ts, src/webhooks.ts, src/settings.ts, src/importers.ts, src/agent.ts, src/validation.ts, src/cli.ts
  • portal/src/App.tsx, api.ts, and the view inventory
  • Dockerfile, docker-compose.yml, tsconfig.json, .eslintrc.json, .github/workflows/ci.yml, both package.json files

Executed

  • npx vitest run — the full suite, multiple times and under --poolOptions.forks.singleFork
  • npx tsc --noEmit — passes cleanly
  • npm run lint — fails (recorded as G3)
  • Queried the live gateway/data/grcstudio.db read-only to confirm seeded users, the published bundle, and its test results

Extracted mechanically — route inventory, database tables, domain type unions, environment variables, framework list, webhook events, IaC fixtures, portal views, and the knowledge-base count are pulled from source by script rather than transcribed, so the documented lists cannot silently drift.

Between the code and the in-repo documentation#

GRCStudio ships 3,265 lines of its own documentation under docs/. This set was written independently and does not modify it. Two things are worth flagging to whoever maintains it:

  1. README.md and docs/02-api-reference.md claim "all 42 endpoints". The source defines 61 — the in-repo reference predates roughly 19 routes, including the entire auth module (G24).
  2. Two source comments assert security guarantees that do not exist — "In production, requires admin token" on register, and "Only works in dev mode" on seed-passwords. Neither check is implemented (G23). A reviewer skimming for issues would read those and move on.

Defects surfaced by this review#

Reading and running the code turned up issues that are product defects, not documentation problems. All are in known-gaps.md with file references and reproduction assertions in the validator. The ones that change a deployment decision:

IDFindingSeverity
G14POST /api/auth/register is unauthenticated in every mode and accepts a caller-chosen role, including admin🔴
G5POST /api/auth/seed-passwords is unauthenticated, sets a known default password on the three seeded users, and returns it in the response body🔴
G13Every user-compiled bundle inherits a failing t-cfn-bad test, and publish is blocked while any test fails — users cannot ship a policy they compiled🔴
G4Dev mode — the default — has no authentication; identity is an unverified header🔴
G1 / G2docker compose up cannot work: portal/Dockerfile is missing, and the gateway image starts a dist/ its build never emits🔴
G3npm run lint fails, so CI is red on every push and gates nothing🔴
G10One admin fills both PR approval slots, bypassing two-person review; publish and reject have no role check🟠
G12CloudFormation targets compile to Rego guarded on iac_provider == "kubernetes" and can never fire under OPA🟠
G15save() deletes audit, decision, and scan rows outside the in-memory window — history is lost from storage, not merely unloaded🟠
G6Whole-state persistence requires a single writer; OPA CLI mode blocks the event loop on the hot path🟠

Worth stating plainly alongside that list: these are configuration and route-wiring errors, not design errors. The compiler, the dual-engine consistency model, the approval workflow, and the audit chain are well built and well tested. Most of the P0 items are a few lines each.

Confidence and limitations#

High confidence — anything mechanically extracted or read directly: route inventory, schema, configuration, the compile and evaluation paths, type unions, enforcement semantics, auth wiring, and the defects in check 8, each of which has a reproduction assertion.

Verified by execution — the test suite (87/87), typecheck, lint failure, and the seeded bundle's stored test results.

Medium confidence — paths described from code but not executed end to end: Claude extraction and the live agent runner (no API key was used), OPA server mode (OPA_SERVER_URL), MCP/OpenAPI/A2A import against real endpoints, and webhook delivery.

Not assessed — runtime performance under load, the portal's visual behaviour (no browser session was run against a live gateway), dependency vulnerability status, and whether the 18 control templates faithfully represent the regulations they cite. That last one is a legal question, not an engineering one, and it should be reviewed by whoever owns compliance.

Explicit scope boundary. No file in GRCStudio was created, modified, or deleted. The validator asserts this on every run.

Keeping this current#

  1. Run node scripts/validate-docs.js after any change to GRCStudio.
  2. Run node scripts/build-site.js after editing any Markdown — check 12 fails while the HTML lags behind the source.
  3. A failure names the specific drift: routes added, tables created, env vars introduced, type-union values changed, links broken.
  4. When a check in section 8 fails, that is good news — the defect it asserts has been fixed. Remove the entry from known-gaps.md, remove the assertion, and note the fix here.
