1. Regulatory ingestion & intent extraction 🟡#

Turns prose into structured ControlObjective records. Two extractors, same output schema.

Deterministic keyword extractor (always available) — a knowledge base of 18 control templates keyed by phrases found in the source text ("article 32", "security of processing", "data minimisation"). A document mentioning any keyword yields that template as an extracted control with a confidence score.

Coverage by framework:

FrameworkTemplatesDomain
SOC 24Enterprise Security
GDPR3Data Protection (EU)
NIST CSF 2.03Operational Integrity
CCPA / CPRA2Data Protection (California)
ISO 27001:20222Enterprise Security
HIPAA Security Rule2Healthcare
PCI DSS v42Payments

Claude extraction (with an ANTHROPIC_API_KEY) — reads arbitrary regulatory text using a schema-constrained structured output. The emitted JSON is sanitised — operators, check types and regexes validated — before it can reach the compiler. Model is selectable from claude-opus-4-8, claude-sonnet-5, claude-haiku-4-5.

Five regulatory excerpts ship bundled — GDPR (Articles 5, 30, 32), SOC 2 (CC6 & CC7), HIPAA (§164.312), PCI DSS v4 (Requirements 1 & 3), and NIST CSF 2.0 (PROTECT). The first two are pre-ingested, approved, compiled and published as bundle v1 at seed, so the platform is alive on first boot.

⚠️ Without an API key you are limited to the 18 templates and to documents whose wording matches their keywords. That is a working baseline, not framework coverage — a GDPR document mentioning Article 25 produces nothing, because no template matches it.

2. Human verification gate 🟢#

Extracted controls land in status: "extracted" and compile into nothing. A compliance officer reviews each one and sets approved or rejected; only approved controls reach the compiler. The reviewer id and timestamp are recorded on the control and written to the audit chain.

This is the structural guarantee that no LLM output becomes enforced policy without a person saying yes.

3. Deterministic compiler 🟢#

Approved ControlObjectives → two Rego modules. No LLM is involved past this point; the same controls always produce byte-identical Rego.

Static stream (package grc.static) — one deny contains v if { … } rule per condition, per resource type, per control. Provider-aware: Terraform iterates input.resource_changes and reads change.after; Kubernetes iterates input.items and matches on kind; CloudFormation walks Resources and reads Properties.

Ten condition operators, each with a matching Rego rendering and TypeScript implementation:

OperatorMeaning
exists / absentValue at the dot-path must be present / missing
eq / neqDeep equality against a literal
in / not_inMembership in a list
gte / lteNumeric bounds
regexRE2 match on the value at the path
forbid_patternRE2 match against the JSON of the whole resource — must not match

Runtime stream (package grc.runtime) — default allow := false, with allow if count(deny) == 0. Five check types:

CheckBlocks
tool_scopeA tool not in the calling agent's allowed_tools
pii_egressPII patterns in parameters bound for an external: true tool
classification_egressConfigured data classifications (e.g. restricted, confidential) leaving to an external tool
step_budgetTask step count above maxSteps (default 20) — the agent-drift guard
tool_denylistGlobally forbidden tool names

Generated Rego is import rego.v1 and carries provenance comments naming the source article and control title.

4. Dual-engine evaluation & semantic consistency 🟢#

The differentiator, and it is real.

Every compile auto-generates a test suite — 6 IaC fixtures plus 9 runtime scenarios, each labelled with an expected verdict — and runs every test through both engines:

  • OPA — the compiled Rego, evaluated by the real opa binary (auto-discovered at /opt/homebrew/bin/opa, /usr/local/bin/opa, or on PATH), or by a persistent OPA server when OPA_SERVER_URL is set
  • Builtin — a hand-written TypeScript evaluator implementing the same semantics directly over the ControlObjective structures

semanticConsistency — the percentage of tests where the two agreed — is stored on the bundle and shown in the portal. It is null when OPA is unavailable, so the number never lies about having been measured.

At enforcement time OPA is preferred; if it throws, the error is logged and the builtin evaluator answers instead — the request never fails because a policy engine did. Operators can force either engine from Settings (auto / opa / builtin).

⚠️ Note what consistency measures: agreement on the generated suite, whose fixtures are fixed. It is strong evidence the two implementations agree on the shapes it exercises — it is not a proof of equivalence across arbitrary inputs.

5. Atomic Compliance PR workflow 🟢#

Compiling opens a ChangeRequest. Publishing requires two independent approvals — security and aiops — and neither role can supply both. Reject closes it. Publish sets the bundle active and it is live at both enforcement points immediately.

POST /api/bundles/:id/rollback reactivates any previous bundle version; history is retained with per-version test results and consistency scores.

Every transition is written to the hash-chained audit log and fires a webhook (pr.approved, pr.rejected, bundle.published, bundle.rollback).

6. Static IaC scanner 🟢#

Three providers, two access paths.

ProviderInput shapeResource identity
TerraformPlan JSON — { iac_provider, resource_changes[] }rc.address
Kubernetes{ iac_provider, items[] }metadata.name
CloudFormationTemplate with ResourcesLogical id

In the portal — pick a bundled sample or paste your own, see violations with control, article, resource, severity, and message, and which engine decided.

On the command line — grc scan, designed for pipelines:

npm run scan -- plan.json                  # colourised text
npm run scan -- plan.json --format json    # machine-readable
npm run scan -- plan.json --engine builtin # force an engine

Exit codes: 0 pass · 1 violations (block the deploy) · 2 error.

Scans are recorded with verdict, engine, resource count, and violations; the store keeps the most recent 100.

7. Runtime agent gateway 🟢#

POST /api/gateway/authorize — the authorization decision point for agent tool calls.

The gateway builds an envelope from the registry and the request:

{ "action": "tool_call", "tool": "send_email",
  "agent": { "id": "agent-support", "role": "support",
             "allowed_tools": ["…"], "scopes": ["…"] },
  "tool_meta": { "external": true, "data_access": "pii" },
  "params_text": "…", "data_classification": "internal", "step_count": 3 }

…evaluates it against the active bundle's runtime stream, and returns allow/deny with a reason per violated control (article, message, severity) and the engine that decided.

Unknown tools are treated as external — a conservative default, so a tool absent from the registry cannot slip past egress checks.

Decisions are persisted (most recent 200) and surfaced in the portal's decision stream.

⚠️ This is an authorization endpoint, not an interceptor. Your agent runtime must call it. Nothing prevents an agent from executing a tool without asking.

8. Agent runner 🟡#

Demonstrates the enforcement loop end to end.

With an API key — runs a real Claude agent in a manual tool-use loop. The agent sees the full tool registry; every tool call is authorized by the Policy Gateway before execution, and blocked calls are fed back to the model as errors, so it must adapt its plan. That feedback loop is the interesting part: it shows governance shaping agent behaviour rather than merely logging it.

Without a key — a scripted simulated agent walks the same interception path.

9. Agent & tool registry 🟢#

The governance metadata the runtime stream reasons over.

Agents — id, name, role, description, scopes[], allowedTools[], optional import provenance. Tools — name, description, external (crosses the trust boundary), dataAccess (public / internal / pii), optional provenance.

Seeded with 3 agents and 10 tools spanning support, analytics, and DevOps.

Import from live endpoints (POST /api/import) — three protocols:

KindSourceYields
openapiAn OpenAPI documentOne tool per operation
mcpAn MCP server (initialize + tools/list)One tool per MCP tool
a2aAn A2A agent card at /.well-known/agent.jsonThe agent plus one tool per skill

Because none of these protocols carry governance metadata, imports default to the most restrictive classification — external: true, dataAccess: "pii" — until a human reclassifies. Imported names are slugged and truncated; all fetched metadata is treated as untrusted input, capped at 50 items.

Tools imported from real MCP servers are forwarded via tools/call JSON-RPC rather than returning canned responses, with session management and SSE parsing handled by a shared client module.

10. Policy waivers 🟡#

Time-limited, scoped exceptions.

A waiver names a controlId, a business reason, an expiresAt, and optionally narrows to an agentId, toolName, or resource. Active waivers filter violations out of both the static scanner and the runtime gateway. Waivers auto-expire — getActiveWaivers() flips past-due rows to expired on every read — and can be revoked early.

CSV export and import are provided for bulk management, and creation, expiry, and revocation all fire webhooks.

⚠️ Two things to know. Waiver creation is genuinely role-gated — the handler resolves the caller from state and rejects anyone who is not security or admin, so it holds in dev mode too. But in dev mode the caller is whoever the X-GRC-User header says, and that header is unauthenticated. And a waiver with no scope exempts the control everywhere, for every agent and every resource — scope it unless you mean that.

11. Evidence & audit 🟢#

Hash-chained audit log. Each entry stores SHA-256(id + at + user + action + detail + prevHash). GET /api/audit/verify walks the chain and returns chainIntact, plus the exact index and entry id where it breaks. Tampering with a row invalidates every entry after it.

Evidence export — GET /api/evidence/export returns the full posture as one JSON document: controls, bundles (with Rego and test results), waivers, runtime decisions, scan records, and the audit log.

Reports summary — GET /api/reports/summary aggregates coverage by framework, control status, bundle history, decision and scan verdicts.

Retention is bounded by design: 300 audit entries, 200 decisions, 100 scans (all configurable).

12. Cross-framework mapping 🟢#

Six concepts — encryption at rest, network access controls, access control & least privilege, data minimisation & purpose limitation, audit logging & monitoring, and AI/agent governance & autonomy limits — each mapped to the equivalent article in all seven supported frameworks.

GET /api/crossmap returns the mappings with a coverage percentage against what you have actually extracted. GET /api/crossmap/gaps inverts it: for each concept you partially cover, which frameworks' equivalents you are still missing. This is the "satisfy SOC 2 and you are most of the way to ISO 27001" argument, computed rather than asserted.

15. Authentication & identity 🟡#

Two modes.

Dev mode (default when NODE_ENV !== "production") — identity comes from the X-GRC-User header, defaulting to u-priya. No password. The user switcher in the portal is simply changing this header.

Production mode (NODE_ENV=production, or AUTH_ENABLED=true) — JWT bearer tokens, bcrypt-hashed passwords, register / login / change-password / me endpoints.

Four roles: compliance, security, aiops, admin.

⚠️ Read G4 before relying on roles. In dev mode any caller can claim any identity by setting X-GRC-User, and req.authUser.role is hard-coded to compliance regardless of who the header names. Routes that enforce roles correctly do so by re-resolving the user from state themselves; the exported requireRole middleware would skip the check in dev mode, and is currently not used by any route.

16. Hardening already in place 🟢#

Worth crediting, because it is unusual at this stage:

  • helmet security headers; CORS restricted to configured origins in production
  • Two-tier rate limiting — 200 req/min general, 10 req/min on LLM extraction, agent runs, and imports
  • 2 MB request body cap
  • Zod schemas validating every mutating request body
  • API keys stored write-only, optionally AES-256-GCM encrypted at rest (SETTINGS_KEY), with a documented secrets hierarchy: GCP Secret Manager → settings.json → env → .env
  • Settings persisted separately from state, so "reset demo data" never destroys configuration
  • 87 automated tests (Vitest) across the compiler, engine, service, store, and validation
  • A CI workflow running typecheck, lint, tests, and a portal build
