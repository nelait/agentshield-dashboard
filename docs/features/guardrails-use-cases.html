UC-01 Create Guardrail Profile
Actor: Admin / Editor Precondition: Authenticated with editor or admin role

Flow

  1. User opens the Guardrails page → Profiles & Rules tab.
  2. User clicks "New Profile".
  3. Modal opens with fields: Name, Description, Enforcement Mode (Block or Log Only).
  4. User fills the form and clicks "Create Profile".
  5. Frontend calls POST /guardrails/profiles.
  6. Backend inserts a row into guardrail_profiles with is_active = true.
A new guardrail profile exists. It has no rules and no agent assignments until configured.
UC-02 Add Rule to Profile
Actor: Admin / Editor Precondition: At least one guardrail profile exists

Flow

  1. User selects a profile from the list (detail panel opens on the right).
  2. User clicks "Add Rule".
  3. Modal opens with fields: Name, Rule Type, Scope, Severity, Description, and type-specific config.
  4. User selects a rule type — the config editor dynamically updates:
    • Content Filter: Keyword list, case sensitivity toggle
    • PII Shield: Checkboxes for SSN, Credit Card, Email, Phone, DOB, MRN
    • Prompt Injection: Extra regex patterns
    • Topic Boundary: Allowed/blocked topics
    • Token Limit: Max tokens input
    • Custom Regex: JSON array of patterns
    • Output Format: JSON required toggle, max length
  5. User clicks "Add Rule".
  6. Frontend calls POST /guardrails/profiles/:id/rules.
  7. Backend inserts into guardrail_rules.
The rule is added to the profile and will be evaluated during enforcement and test runs.
UC-03 Assign Guardrail to Agent
Actor: Admin / Editor Precondition: At least one profile and one registered agent exist

Flow

  1. User navigates to the Agent Assignments tab.
  2. User selects an agent from the dropdown.
  3. User selects a guardrail profile from the dropdown.
  4. User clicks "Assign".
  5. Frontend calls POST /guardrails/assign.
  6. Backend inserts into agent_guardrails. ON CONFLICT DO NOTHING prevents duplicates.

Alternative Flows

  • A1 — Agent already assigned: No duplicate created. Operation is idempotent.
  • A2 — Multiple profiles per agent: All profiles are evaluated during enforcement.
The agent's requests will be evaluated against the profile's rules during gateway invocation.
UC-04 Remove Guardrail Assignment
Actor: Admin / Editor Precondition: A profile-to-agent assignment exists

Flow

  1. User selects a profile in the Profiles & Rules tab.
  2. Under "Assigned Agents", clicks the ✕ button next to an agent name.
  3. Frontend calls DELETE /guardrails/assign.
  4. Backend deletes the agent_guardrails row.
The agent is no longer protected by that guardrail profile.
UC-05 Real-Time Input Guardrail Enforcement
Actor: Gateway (guardrailEnforcer middleware) Precondition: Agent has active guardrail profile with enabled rules

Flow

  1. Client sends POST /api/v1/gateway/agent/:slug/invoke.
  2. guardrailEnforcer middleware intercepts the request.
  3. guardrailsService.evaluateInput(slug, body) resolves profiles, fetches rules, evaluates content.
  4. Returns { allowed, violations[], sanitized }.

Alternative Flows

  • A1 — No guardrails assigned: Returns { allowed: true }. Proceeds unmodified.
  • A2 — Block mode (critical/high): 422 response with GUARDRAIL_VIOLATION. Audit-logged.
  • A3 — Log-only mode: Proceeds. Violation is audit-logged and traced via OpenTelemetry.
  • A4 — Medium/low severity: Always logged, never blocks.
  • A5 — Service error (fail-open): Error logged, request proceeds. Never a single point of failure.
Allowed requests proceed. Blocked requests get 422. All violations are audit-logged.
UC-06 Run Guardrail Tests
Actor: Admin / Editor Precondition: At least one guardrail profile with rules exists

Flow

  1. User navigates to the Test Runner tab.
  2. Selects a guardrail profile from the dropdown.
  3. Adds test cases with: Input text, Expected Verdict, Direction, Description.
  4. Clicks "▶ Run Guardrail Tests".
  5. Frontend calls POST /guardrails/profiles/:id/test.
  6. Backend evaluates each test case against profile rules.
  7. Results display: Pass Rate ring, metric cards, per-test breakdowns.

Alternative Flows

  • A1 — All tests pass: 100% in green.
  • A2 — False negative: Expected block but got pass — gap in rules.
  • A3 — False positive: Expected pass but got block — overly aggressive.
Test run results are stored and visible in the test run history table.

Actor: Any authenticated user

Flow

  1. User navigates to the Test Runner tab.
  2. Test Run History table loads via GET /guardrails/test-runs.
  3. Table shows: Date, Profile, Agent, Tests (pass/fail/total), Pass Rate, Status.
User has visibility into historical guardrail test effectiveness.
UC-08Edit Guardrail Profile
Actor: Admin / Editor

Flow

  1. User clicks the pencil icon on a profile card.
  2. Edit modal opens pre-filled with current config.
  3. User modifies fields and clicks "Update Profile".
  4. Frontend calls PUT /guardrails/profiles/:id.
Profile configuration is updated. Rules and assignments are preserved.
UC-09Delete Guardrail Profile
Actor: Admin only

Flow

  1. User clicks the trash icon on a profile card.
  2. Confirmation dialog: "Delete this guardrail profile and all its rules?"
  3. Frontend calls DELETE /guardrails/profiles/:id.
  4. ON DELETE CASCADE removes rules, assignments, and test runs.
Profile, rules, assignments, and test history are permanently removed.
UC-10Delete Guardrail Rule
Actor: Admin

Flow

  1. User selects a profile → views rules in the detail panel.
  2. Clicks the trash icon on a rule.
  3. Frontend calls DELETE /guardrails/rules/:id.
Rule is removed from the profile and no longer evaluated.

UC-12Multi-Format Payload Parsing
Actor: GuardrailsService (automatic)

Flow

  1. Plain string — Used directly.
  2. { prompt: "..." } — Extracts prompt field.
  3. { input: "..." } — Extracts input field.
  4. OpenAI format — Concatenates messages[].content.
  5. Anthropic format — Concatenates content[].text.
  6. Fallback — JSON-stringifies the entire payload.
All agent protocols (REST, OpenAI, Anthropic, MCP) supported without protocol-specific config.
Phase 3 — YAML Guardrails-as-Code
UC-13 Export Guardrail Profile as YAML Phase 3
Actor: Admin / Editor / Viewer Precondition: A profile with at least one rule exists

Flow

  1. User selects a profile in the Profiles & Rules tab.
  2. Clicks the "↓ YAML" button in the profile detail header.
  3. Frontend calls GET /guardrails/profiles/:id/yaml.
  4. Backend fetches profile, rules, and assigned agents.
  5. YamlGuardrailParser.generateYaml() converts to human-readable YAML with header comment.
  6. Modal opens with syntax-highlighted YAML.
  7. User can Copy to clipboard or Download .yaml file.

Example Output

# AI Sure — Guardrail Profile
# Generated: 2026-07-16
guardrail:
  name: PII & Safety Shield
  version: '1.0'
  mode: block
  rules:
    - id: ssn-detection
      name: SSN Detection
      type: pii-shield
      severity: critical
      scope: both
User has a YAML file that can be committed to Git, shared with teammates, or imported into another AI Sure instance.
UC-14 Import Guardrail Profile from YAML Phase 3
Actor: Admin / Editor Precondition: Authenticated with editor or admin role

Flow

  1. User clicks "Import YAML" in the Guardrail Profiles header bar.
  2. Import modal opens with file upload and paste options.
  3. User clicks "🔍 Preview".
  4. Frontend calls POST /guardrails/preview-yaml.
  5. Backend validates YAML schema (required fields, valid types, valid severities).
  6. If valid: preview panel shows profile name, mode, rule count, rule cards, and conflict warnings.
  7. User clicks "Import Profile".
  8. Frontend calls POST /guardrails/import-yaml.
  9. Backend creates the profile and all rules.
  10. Modal closes and the profile list refreshes.

Alternative Flows

  • A1 — Invalid YAML syntax: Parse error displayed. Import disabled.
  • A2 — Schema validation failure: Missing guardrail.name or invalid types. Errors listed.
  • A3 — Name conflict: ⚠️ "Name exists" badge shown. Import disabled.
  • A4 — API error: Backend returns 409 or 500. Error banner shown.
A new profile with all rules is created from YAML. Appears in the list and can be assigned to agents.
UC-15 Preview / Validate YAML Without Saving Phase 3
Actor: Admin / Editor / Viewer Precondition: User has YAML content to validate

Flow

  1. User opens the Import YAML modal.
  2. Pastes or uploads YAML content.
  3. Clicks "🔍 Preview".
  4. Frontend calls POST /guardrails/preview-yaml.
  5. Backend returns: valid, errors[], nameConflict, summary, rules[].
  6. Preview panel renders results.
No data is persisted. User sees exactly what would be imported before committing.
UC-16 Upload YAML File from Filesystem Phase 3
Actor: Admin / Editor Precondition: User has a .yaml or .yml file

Flow

  1. User opens the Import YAML modal.
  2. Clicks "Choose File" and selects a .yaml or .yml file.
  3. FileReader API reads the file content as text.
  4. YAML content is loaded into the code editor textarea.
  5. Preview and error states are reset.
  6. User proceeds to preview/import as in UC-14.
File content is loaded into the editor. No network call until user clicks Preview or Import.
UC-17 YAML Round-Trip Fidelity Phase 3
Actor: Admin / Editor Precondition: A guardrail profile with rules exists

Flow

  1. User exports a profile as YAML (UC-13).
  2. Downloads the .yaml file.
  3. Imports the same YAML via Import modal (UC-14) — after changing the name.
  4. A new profile is created with identical rules.
Imported profile's rules match the original in type, scope, severity, and configuration. Full fidelity preserved.
