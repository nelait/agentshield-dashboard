2. Per-Module Analysis

2.1 Policy Enforcer (Stage 4) — Blocking, Synchronous

Role: Decides "Can this user call this agent?"

StepOperationDB QueriesLatency
1getModuleStatus('policies')0–1 (cached 30s)~0–2ms
2RegistryService.getAgent(slug)1 query~2–5ms
3policyService.evaluate(context)1 query — SELECT * FROM policies WHERE is_active = true~3–10ms
4In-memory rule evaluation (JSON matcher + OPA WASM)0 queries~0.1–0.5ms

⚠️ Important
No caching on policies. Every request queries ALL active policies from the DB and iterates through them. For systems with many policies, this grows linearly. OPA WASM evaluation (Phase 1) adds ~0.1–0.4ms to the in-memory evaluation step but eliminates the need for JS-based rule matching.

2.2 Budget Checker (Stage 5) — Blocking, Synchronous

Role: Decides "Has this user exceeded their budget?"

StepOperationDB QueriesLatency
1getModuleStatus('cost_management')0–1 (cached 30s)~0–2ms
2For each scope (user, team, dept, agent, global)1 query PER SCOPE~2–5ms each
3Period expiry check + possible reset0–2 queries~0–10ms
Total (worst case: 5 scopes)5–7 queries~10–35ms
🔴 Warning
This is the most expensive middleware. In the worst case (user + team + department + agent + global), it fires 5 separate DB queries, each a sequential SELECT with no batching.

2.3 Guardrail Enforcer (Stage 5.5) — Blocking, Synchronous

Role: Decides "Does this content violate any rules?"

StepOperationDB QueriesLatency
1getModuleStatus('guardrails')0–1 (cached 30s)~0–2ms
2Resolve agent slug → ID1 query~1–3ms
3getAgentGuardrails(agentId)1 query — JOIN profiles~3–8ms

ℹ️ Note
The rule evaluation itself is fast (regex matching, keyword search). The cost is in the 3–4 DB round-trips to fetch profiles and rules. LLM Judge is intentionally skipped in real-time mode.

2.4 Compliance Sampler (Stage 6) — Non-Blocking, Async ✅

Role: Probabilistically samples request/response pairs for audit.

StepOperationDB QueriesLatency Impact
1getModuleStatus('compliance')0–1 (cached)~0–2ms
2Hooks res.json() and calls next()00ms — does NOT block
3After agent responds (async fire-and-forget)1–20ms — never delays response
💡 Tip
Compliance is the gold standard. It hooks into res.json() and runs after the response is sent. The client never waits for compliance logic. This pattern should be the model for future middleware.

2.5 Evaluation Module — NOT in the Pipeline ✅

Role: Runs periodic quality assessments via LLM-as-a-Judge.

Evaluations call agents directly via _invokeAndCapture(), bypassing the gateway middleware entirely. They are a batch/scheduled process, not a per-request check.

⛔ Caution
On every gateway call, the system issues 12–18 DB queries across policy, budget, and guardrail checks. At scale (>100 req/s), this creates significant connection pool pressure and adds ~35–80ms of latency before the request even reaches the agent.

4. MCP-Specific Impact

MCP (Model Context Protocol) agents go through the exact same middleware chain as REST agents. The proxy flow:

Client → Middleware Chain → proxy.js → invokeMcpAgent() → SSE connect → list_tools → call_tool → Response

MCP calls are inherently slower than REST because they involve:

MCP StepLatency
SSE connection establishment~50–200ms
Tool listing handshake~100ms
Tool invocation~500ms – 10s
Middleware overhead~35–80ms (5–15% of total)

The middleware overhead is proportionally smaller for MCP (~5–15% of total) but still creates unnecessary DB connection pool pressure at scale.

6. Latency Optimization Strategies

Strategy 1: Cache Policy Decisions High Impact, Low Risk

Problem: policyService.evaluate() queries ALL active policies on every call.

Solution: Cache the policy list with a 15-second TTL, similar to the module toggle cache.

// PolicyService — add cache
class PolicyService {
    constructor() {
        this._policyCache = null;
        this._policyCacheExpiry = 0;
    }

    async _getActivePolicies() {
        if (this._policyCache && Date.now() < this._policyCacheExpiry) {
            return this._policyCache;
        }
        const { rows } = await db.query(
            `SELECT * FROM policies WHERE is_active = true ORDER BY priority ASC`
        );
        this._policyCache = rows;
        this._policyCacheExpiry = Date.now() + 15000; // 15s TTL
        return rows;
    }
}

Strategy 2: Batch Budget Queries High Impact, Medium Risk

Problem: checkBudget() fires up to 5 sequential DB queries, one per scope.

Solution: Replace N queries with a single WHERE scope_id = ANY($1) query.

async checkBudget(userId, teamId, departmentId, agentId) {
    const scopeIds = [userId, teamId, departmentId, agentId, 'global'].filter(Boolean);

    // ONE query instead of 5
    const { rows } = await db.query(
        `SELECT * FROM budgets
         WHERE scope_id = ANY($1) AND is_active = true AND period_start <= NOW()`,
        [scopeIds]
    );

    // Group results by scope and evaluate
    for (const budget of rows) {
        if (this._isPeriodExpired(budget)) {
            await this._archiveAndResetBudget(budget);
            continue;
        }
        // ... existing limit checks
    }
}

Strategy 3: Pre-compute Guardrail Rule Cache High Impact, Medium Risk

Problem: _evaluate() does 3–4 sequential queries: resolve slug → get profiles → get rules per profile.

Solution: Cache the full agent → profiles → rules tree with a 30-second TTL.

Strategy 4: Parallel Middleware Execution Moderate Impact, High Risk

Problem: Middleware runs serially: Policy → Budget → Guardrails.

Solution: Run independent checks in parallel using Promise.all().

MetricBefore (Serial)After (Parallel)
Latencysum(P + B + G) = ~33–72msmax(P, B, G) = ~15–35ms
QueriesSame totalSame total
⚠️ Trade-off
If Policy denies, Budget and Guardrail queries are wasted. In the serial model, Policy denial short-circuits and saves downstream work. Parallel execution trades wasted queries for reduced latency on the happy path.

Strategy 5: Redis-Backed Decision Cache Very High Impact, Higher Complexity

Problem: All caches are in-memory and process-local. In multi-instance deployments, cache invalidation doesn't propagate.

Solution: Use Redis as a shared cache layer with Pub/Sub for cross-instance invalidation.

Strategy 6: Compiled Rule Engine Future, Very High Impact

For organizations with many policies/guardrails, pre-compile rules into decision trees at save time instead of interpreting them at request time. This is what OPA (Open Policy Agent) does — AgentShield already has OPA integration patterns in the design docs.

8. Key Takeaways

#Finding
1Evaluations never run on gateway calls. They're dashboard-only batch jobs. Zero latency concern.
2Compliance is already async-optimized. It hooks res.json() and runs after the response. No changes needed.
3Policy, Budget, and Guardrails are the latency culprits. They collectively issue 12–18 DB queries per request, all synchronous and blocking.
4None of these modules share query results. Policy fetches agent info, then Guardrails fetches it again independently.
5The module toggle cache (30s TTL) is the only caching that exists. Everything else hits the DB cold on every request.
6MCP calls are proportionally less affected (~5–15% overhead) because the MCP protocol itself adds 200–500ms. But DB pool pressure is identical.
