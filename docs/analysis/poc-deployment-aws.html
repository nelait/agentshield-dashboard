3. Infrastructure Setup (Step-by-Step)

1

VPC & Networking

~5 minutes
# Set region
export AWS_REGION=us-east-1

# Create VPC with public + private subnets (using default VPC is also fine for POC)
aws ec2 create-vpc --cidr-block 10.0.0.0/16 --tag-specifications \
  'ResourceType=vpc,Tags=[{Key=Name,Value=agentshield-vpc}]'

# Create 2 private subnets (for RDS, ElastiCache, ECS tasks)
aws ec2 create-subnet --vpc-id $VPC_ID --cidr-block 10.0.1.0/24 --availability-zone us-east-1a
aws ec2 create-subnet --vpc-id $VPC_ID --cidr-block 10.0.2.0/24 --availability-zone us-east-1b

# Create 2 public subnets (for ALB)
aws ec2 create-subnet --vpc-id $VPC_ID --cidr-block 10.0.10.0/24 --availability-zone us-east-1a
aws ec2 create-subnet --vpc-id $VPC_ID --cidr-block 10.0.11.0/24 --availability-zone us-east-1b

# Create Internet Gateway + NAT Gateway for outbound from private subnets
aws ec2 create-internet-gateway
aws ec2 create-nat-gateway --subnet-id $PUBLIC_SUBNET_1 --allocation-id $EIP_ID
💡 Shortcut: AWS Copilot CLI
For a faster POC, use aws copilot which auto-generates VPC, subnets, ALB, and ECS cluster in one command. See Step 4 below.
2

Database & Cache

~10 minutes
# Create RDS subnet group
aws rds create-db-subnet-group \
  --db-subnet-group-name agentshield-db-subnets \
  --subnet-ids $PRIVATE_SUBNET_1 $PRIVATE_SUBNET_2 \
  --db-subnet-group-description "AgentShield DB subnets"

# Create security group for RDS
aws ec2 create-security-group --group-name agentshield-db-sg \
  --description "Allow PostgreSQL from ECS tasks" --vpc-id $VPC_ID
aws ec2 authorize-security-group-ingress --group-id $DB_SG \
  --protocol tcp --port 5432 --source-group $ECS_SG

# Create RDS PostgreSQL instance
aws rds create-db-instance \
  --db-instance-identifier agentshield-db \
  --db-instance-class db.t4g.small \
  --engine postgres --engine-version 16 \
  --master-username agentshield \
  --master-user-password "$(openssl rand -base64 24)" \
  --allocated-storage 20 --storage-type gp3 \
  --db-name agentshield \
  --vpc-security-group-ids $DB_SG \
  --db-subnet-group-name agentshield-db-subnets \
  --no-publicly-accessible \
  --backup-retention-period 7

# Create ElastiCache Redis
aws elasticache create-cache-cluster \
  --cache-cluster-id agentshield-redis \
  --cache-node-type cache.t4g.micro \
  --engine redis --engine-version 7.1 \
  --num-cache-nodes 1 \
  --cache-subnet-group-name agentshield-cache-subnets \
  --security-group-ids $CACHE_SG

Deploy Test Agents (ECS Fargate)

~15 minutes
# Build and push each agent image
for agent in echo-agent finance-agent support-agent code-review-mcp weather-mcp; do
  docker build -t agentshield-$agent ./agents/$agent
  docker tag agentshield-$agent:latest $ACCOUNT_ID.dkr.ecr.us-east-1.amazonaws.com/agentshield-$agent:latest
  docker push $ACCOUNT_ID.dkr.ecr.us-east-1.amazonaws.com/agentshield-$agent:latest
done

# Register task definitions for each agent (0.25 vCPU, 512 MB)
# Create ECS services with ALB target groups
# Each agent gets its own target group on the shared ALB
# Path-based routing: /echo/* → echo-agent, /finance/* → finance-agent, etc.

# Or deploy each agent as a standalone service with its own internal URL
for agent in echo-agent finance-agent support-agent code-review-mcp weather-mcp; do
  aws ecs create-service --cluster agentshield \
    --service-name $agent \
    --task-definition $agent \
    --desired-count 1 --launch-type FARGATE \
    --network-configuration "awsvpcConfiguration={subnets=[$PRIV_SUB1,$PRIV_SUB2],securityGroups=[$AGENT_SG],assignPublicIp=ENABLED}" \
    --service-connect-configuration "enabled=true,namespace=agentshield,services=[{portName=http,clientAliases=[{port=8080,dnsName=$agent}]}]"
done

# With ECS Service Connect, agents are reachable at:
# http://echo-agent:8080, http://finance-agent:8080, etc.
📋 AWS Service Connect
ECS Service Connect provides DNS-based service discovery within the cluster. AgentShield can reach test agents via their service names (e.g., http://echo-agent:8080) without requiring public endpoints. For external-facing agents, use the ALB with path-based routing.

4. Test Agent Design

We create 6 purpose-built test agents, each designed to trigger specific AgentShield governance features. Together they cover REST, MCP, and external (OpenAI-compatible) protocols.

🔄 Echo Agent
Echoes back any input. Baseline agent for policy, auth, and audit testing.
Protocol: RESTSlug: echo-agentPurpose: Policy enforcement, auth, audit logging
💰 Finance Agent
Returns mock financial data with configurable token usage in responses.
Protocol: REST (with usage object)Slug: finance-agentPurpose: Cost tracking, budget enforcement
📞 Support Agent
Simulates customer support — intentionally returns PII and sensitive data.
Protocol: RESTSlug: support-agentPurpose: Guardrails (PII, profanity, injection)
💻 Code Review MCP
MCP server that exposes code review tools (analyze, lint, security-scan).
Protocol: MCP (SSE transport)Slug: code-review-mcpTools: analyze_code, lint, security_scan
🌤️ Weather MCP
MCP server providing weather data tools. Lightweight, good for health checks.
Protocol: MCP (SSE transport)Slug: weather-mcpTools: get_weather, get_forecast
🧠 OpenAI Proxy
Proxies to a real OpenAI-compatible endpoint. Returns real usage data.
Protocol: REST (OpenAI-compatible)Slug: openai-proxyAuth: Bearer token (API key)
💡 Agent Source Code
The test agent implementations are identical across AWS, Azure, and GCP — they are standard Node.js Express apps packaged in Docker containers. See the GCP POC Guide § 5 for full source code of each agent.

7. Demo 1: Agent Registry Phase 1

Scenario 1.2 — Health monitoring
Prove: AgentShield actively monitors agent availability
  1. Wait 30 seconds for health checks to run
  2. Verify Echo Agent and Weather MCP show "healthy" status (green)
  3. Scale agent service to 0 tasks: aws ecs update-service --desired-count 0
  4. Wait for 3 consecutive failures — agent shows "unhealthy" (red)
  5. Scale back to 1 — status returns to "healthy" automatically
✅ Health status transitions: healthy → unhealthy → healthy. Dashboard updates in real time.
Scenario 1.3 — Agent invocation through gateway
Prove: Requests are proxied transparently through AgentShield
  1. Invoke Echo Agent via gateway: POST /api/v1/gateway/agents/echo-agent/invoke
  2. Verify response contains X-Forwarded-By: AgentShield
  3. Invoke Code Review MCP — verify MCP tool listing and tool call works
✅ Transparent proxying works for both REST and MCP protocols.
