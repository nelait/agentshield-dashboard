Capability Matrix#

Every shipped capability, what it actually does in code, and an honest maturity rating.

Maturity legend

1. Agent Registry 🟢#

The system of record for every agent under governance.

AspectDetail
Protocolsrest, mcp, a2a, grpc (DB check constraint)
Classificationexternal vs internal; free-text vendor; JSON capabilities array
IdentityHuman name + URL-safe slug (unique); the slug is the address in every gateway URL
Upstream authPer-agent auth_config JSONB: bearer (token) or api_key (custom header name)
HealthBackground checker every 30 s (HEALTH_CHECK_INTERVAL_MS), 5 s timeout, marks unhealthy after 3 consecutive failures

Inactive or unhealthy agents are refused at the gateway with 503 before any upstream call is attempted — in both the REST gateway and the MCP proxy.

2. Policy Engine 🟢#

Attribute-based access control over agent invocation.

Two authoring formats, one evaluation pass. Active access_control policies are loaded ordered by priority ASC; the first policy that matches decides, and evaluation stops.

  • JSON policies — three condition groups evaluated against the request context: lte, exists, between (with a special time/hour form that reads the server clock)
    • subjects — all must match against context.user (AND)
    • resources — at least one must match against context.agent/context.workflow (OR)
    • conditions — all must match against the whole context (AND)
    • Operators: eq, neq, in, not_in, contains, starts_with, gt, gte, lt,
    • Empty/placeholder conditions are filtered out rather than failing the match
  • Rego policies — source is syntax-validated, compiled to WASM by the opa binary (v1.4.2, installed in the Docker image), and the WASM blob is stored in the policies row. At request time the WASM module is instantiated and fed an input document of {user, agent, workflow, action, timestamp}. A Rego policy that produces neither allow nor deny is treated as not matched and evaluation continues to the next policy.

The default matters:

SituationOutcome
Zero active access-control policies existAllow — "No policies defined — default allow"
Policies exist but none matchedDeny — "No matching policy — default deny"

Denials return 403 POLICY_DENIED and are written to the audit log with the matched policy name and reason.

3. Guardrails 🟡#

Content enforcement on the payload, organised as profiles (containing rules) assigned to agents.

Eight rule types:

TypeWhat it doesConfig keys
content_filterSubstring match against a blocklistkeywords[], caseSensitive
pii_shieldRegex detection of SSN, credit card, email, phone, DOB, MRNpatterns[], customPatterns[]
prompt_injection15 built-in jailbreak/injection regexes ("ignore previous instructions", "developer mode", DAN, etc.)extraPatterns[]
topic_boundaryKeyword allow-list / block-list on subject matterallowedTopics[], blockedTopics[]
token_limitSize ceiling using a ~4-chars-per-token estimatemaxTokens
custom_regexArbitrary user patterns with labelspatterns[{pattern,flags,label}]
output_formatResponse must parse as JSON and/or stay under a length caprequireJson, maxLength
llm_judgeSemantic evaluation by a model(see caveat below)

Scope — each rule applies to input, output, or both.

Blocking semantics — a violation blocks the request only when both are true: the profile's mode is block, and the rule's severity is critical or high. Everything else is recorded as a violation and allowed through. Blocks return 422 GUARDRAIL_VIOLATION with the full violation list.

Authoring — profiles can be created in the UI, or imported/exported as YAML (/guardrails/import-yaml, /guardrails/preview-yaml, /guardrails/profiles/:id/yaml). A built-in test runner executes labelled test cases against a profile and records pass/fail per rule in guardrail_test_runs.

⚠️ Two caveats that determine the rating.

  1. llm_judge is explicitly skipped during live enforcement — the evaluator returns "LLM judge skipped in real-time mode". Semantic guardrails work in test runs and in the Evaluation module, not in the request path.
  2. Guardrail enforcement fails open: if the guardrail service throws, the request proceeds. This is a deliberate availability choice, documented in the code as "don't block requests if guardrails service errors."

Also note the schema's sanitized field is returned as null — inline PII masking on the inbound path is a stated future item. Outbound redaction does exist; see DLP below.

4. Compliance Engine 🟡#

Two distinct mechanisms share this module.

4a. Passive sampling (runs on live traffic)#

A compliance_config names a framework (sox, hipaa, gdpr, pci_dss, custom), a sample_rate (0–1), a retention period (default 2190 days ≈ 6 years, the HIPAA requirement), and optionally a set of assigned agents. On each gateway response the sampler rolls against the rate; on a hit it stores the request/response pair:

  • SHA-256 hashes of both bodies for tamper evidence
  • Bodies encrypted with AES-256-GCM (key from COMPLIANCE_ENCRYPTION_KEY) into BYTEA
  • PII scan across the combined text; detected types recorded and the sample auto-flagged

Sampling is fully asynchronous and never delays or fails the response.

4b. Active compliance checks (run on demand)#

POST /compliance/configs/:id/run executes the framework's enabled rules against sample inputs. Inputs come from three places: framework-specific built-in samples, a JSON array of samples posted to upload-samples, or custom inputs in the request. (Spreadsheet upload via multer + xlsx exists on a separate route, POST /compliance/rules/upload, and imports rules rather than samples — 5 MB limit, memory storage.) Where an agent is assigned and reachable, the check actually invokes it and evaluates the real response — connection status is reported in every rule result.

Built-in rules: 5 each for SOX, HIPAA, GDPR, PCI-DSS and 3 for custom, seeded into compliance_rules and editable in the console (built-ins can be disabled but not deleted).

4c. NIST OSCAL interoperability 🟢#

  • Import an OSCAL catalog JSON; validate → preview groups → import selected control groups as compliance rules, tagged with oscal_control_id and shown with an OSCAL badge
  • Export a completed check as an OSCAL Assessment Result

⚠️ Rule evaluation is pattern-based, not semantic. sox-1 "Financial Data Integrity" passes when a $-amount regex matches; sox-3 and sox-5 return passed: true unconditionally on the grounds that the platform itself provides the control. This is reasonable as control attestation but should not be presented to an auditor as behavioural verification.

6. Audit Logging 🟢#

  • Append-only at the database level — audit_log carries PostgreSQL rules DO INSTEAD NOTHING on both UPDATE and DELETE. Tampering fails silently rather than succeeding.
  • Every record carries: trace id, event type, actor id/type, resource type/id, action, outcome (allowed/denied/error/info), a JSONB detail blob, client IP, and latency.
  • Event types include api_request, policy_enforcement, budget_enforcement, guardrail_violation, mcp_proxy_request, mcp_proxy_policy_denied.
  • Noise filter — read-only polling traffic (settings, dashboard stats, health, auth, agent list reads) is excluded so the trail stays legible. Mutations on those same paths are still logged.
  • Audit writes are fire-and-forget: a failure never fails the user's request.
  • Console offers filtering, aggregate stats, and a filter-options endpoint.

7. Agent Evaluation 🟡#

A three-layer quality model with an LLM judge and human review.

LayerMetrics
Nodetool selection, parameter precision, plan utility
Sessiontask success, topic adherence, grounding
Systemaverage latency, total tokens, average step count, token efficiency

Judging — the judge model is prompted for chain-of-thought reasoning before each score and must return strict JSON scoring five dimensions 0–10: task_success, tool_selection, reasoning_quality, grounding, safety, plus a confidence and a flags array. A rule-based fallback judge exists for when no LLM connection is configured.

Overall score — a weighted blend, default accuracy 50 / safety 30 / latency 10 / consistency 10, all four weights configurable in Settings → Evaluation, along with the latency scoring tiers. Consistency is derived from the standard deviation across scenario scores; token efficiency from average tokens per scenario.

Simulation personas — five templates generate adversarial and awkward traffic: happy path 🙂, confused 😕, adversarial 😡, edge case 🔄, data-heavy 📊.

HITL — runs produce review items; reviewers accept or override the judge, and the verdicts persist in eval_reviews.

⚠️ Evaluation quality depends entirely on the configured judge model. With no LLM connection in Settings, scoring silently falls back to the rule-based judge, which is much coarser. The UI does not prominently distinguish the two in historical runs.

8. Workflow Orchestration 🟠#

Chain agents into a sequence: workflow_agents rows carry step_order, an is_optional flag, per-step config, and data_flow_rules.

Execution (POST /gateway/workflows/:slug/run) walks the steps in order, passing each agent's response.data as the next agent's input, metering cost per step, and returning the final output plus a per-step latency summary. An inactive agent is skipped when is_optional, and fails the run with 503 when it isn't.

⚠️ Three real limits: execution is strictly sequential (no parallel/fan-out, no branching, no retry), data_flow_rules is persisted but not applied by the executor (output is passed through whole), and workflow-level max_concurrent, daily_limit, and requires_approval are columns with no enforcement code behind them.

9. MCP Gateway 🟢#

Native Model Context Protocol support, not generic HTTP pass-through.

  • Endpoint POST /mcp/:agentSlug, speaking JSON-RPC 2.0
  • Methods handled explicitly: initialize (intercepted — AgentShield merges its own server info with the upstream's capabilities), ping (answered locally), notifications (202, no upstream call), tools/list, tools/call
  • Governance applies to tools/call: policy → guardrails → budget, in that order, with the tool name recorded in the audit action (mcp:tools/call:<toolName>)
  • JSON-RPC error codes: -32001 auth, -32002 agent resolution, -32003 policy denial, -32004 guardrail block, -32005 budget exceeded, -32603 proxy error
  • Transport — SSE and Streamable HTTP upstreams are auto-detected
  • Claude Desktop / Cursor — tools/mcp-bridge.js is a stdio↔HTTP shim so desktop MCP clients connect through the firewall with only a config-file change
  • MCP Explorer in the console lists upstream tools and invokes them with governance on

Note: tools/list is forwarded without policy filtering — callers see the upstream's full tool catalogue, and enforcement happens at call time. See known-gaps.md.

10. Data Loss Prevention (outbound) 🟡#

On the REST gateway's single-agent invoke path, the agent's textual reply (reply, output, or text) is scanned and rewritten before it reaches the caller. Detected values are replaced with [REDACTED:TYPE] placeholders for: SSN, credit card, email, phone, MRN, DOB, IP address. Applied redactions are reported back in meta.dlp.outbound and recorded on the trace span.

⚠️ Scope limit: outbound DLP runs on POST /gateway/agents/:slug/invoke only. Workflow step outputs and MCP tools/call results are not redacted.

12. Observability 🟢#

OpenTelemetry is initialised before every other import in src/index.js, so auto-instrumentation captures HTTP, PostgreSQL, and outbound calls.

Custom spans: agentshield.authenticate, agentshield.policy.evaluate, agentshield.budget.check, agentshield.guardrail.evaluate, agentshield.compliance.sample, agentshield.audit.log, agentshield.agent.invoke, agentshield.agent.forward, agentshield.workflow.run, agentshield.workflow.step, agentshield.mcp-proxy.handle.

Custom metrics: agentshield.requests.total, agentshield.gateway.latency_ms (histogram, 10 ms→10 s buckets), agentshield.policy.decisions, agentshield.policy.denials, agentshield.policy.evaluate_ms, agentshield.auth.failures, agentshield.budget.exceeded.

Token usage is emitted using the gen_ai.* semantic conventions (gen_ai.usage.input_tokens / output_tokens / total_tokens), so any OTLP-compatible backend — Jaeger, Tempo, Datadog, Honeycomb — renders it without custom mapping. The console has an in-app trace detail view; there is no dependency on an external Jaeger UI.

14. Module Toggles 🟢#

Five governance modules — policies, guardrails, compliance, cost_management, evaluations — can be switched off from Settings → Modules. Four of them map to a gateway middleware (policies→policyEnforcer, guardrails→guardrailEnforcer, compliance→complianceSampler, cost_management→budgetChecker); when disabled the middleware returns immediately — the module is fully bypassed, not merely made permissive. evaluations has no middleware; it is an on-demand module, so the toggle only hides the console page. In all five cases the corresponding page disappears from the sidebar.

Status is cached in the backend for 30 s and polled by the dashboard every 60 s, so a toggle takes effect within roughly a minute. Default is enabled, including when the settings lookup fails — a deliberate fail-safe. The UI shows severity-coded warnings, explicit ones for Policies ("ALL gateway requests will be allowed without access checks") and Cost Management.
