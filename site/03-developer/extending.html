Extension Guide#

How to add capability without fighting the architecture. Every recipe follows an existing pattern in the codebase — the file and line references are the working examples to copy.

Add a guardrail rule type#

Example to copy: pii_shield in src/guardrails/service.js.

  1. Write the evaluator. In src/guardrails/service.js, add a private method returning the standard verdict shape:

``js _evaluateSemanticDrift(config, text) { // … return { triggered: true|false, details: 'human-readable explanation' }; } ``

details surfaces in the API response, the audit record, and the console — write it for a security engineer reading an incident, not for a debugger.

  1. Register it in the switch (rule.rule_type) inside _evaluateRule.
  2. Widen the constraint. guardrail_rules.rule_type is a VARCHAR(30) CHECK constraint from migration 009. Add a migration:

``sql ALTER TABLE guardrail_rules DROP CONSTRAINT IF EXISTS guardrail_rules_rule_type_check; ALTER TABLE guardrail_rules ADD CONSTRAINT guardrail_rules_rule_type_check CHECK (rule_type IN (… existing …, 'semantic_drift')); ``

  1. Teach the YAML parser. src/guardrails/yaml-parser.js validates against TYPE_ALIASES; add yours or YAML import will reject the rule.
  2. Add the UI form in agentshield-dashboard/src/pages/Guardrails.jsx — the config editor is driven by a per-type field map.

Keep it synchronous. _evaluateRule is called in the request path and is not awaited. An async check must follow the llm_judge precedent: return { triggered: false } in real-time mode and do the real work in the test runner. If you need async enforcement, that is a middleware change, not a rule change.

Add a report type#

Example to copy: _report_cost_overview in src/reports/service.js.

  1. Add an entry to ReportService.REPORT_TYPES with label, category, icon.
  2. Implement async _report_<key>(filters) returning a plain object. Use this._parseDateRange(filters) for the from/to defaults (last 30 days).
  3. Nothing else. generate() dispatches by naming convention (this['_report_' + type]), the CSV and XLSX exporters walk the returned object generically, and the dashboard's Reports page renders from GET /api/v1/reports/types.

Return arrays of flat rows where you want clean CSV output; nested objects export poorly.

Add a compliance framework#

  1. Extend three CHECK constraints in a migration: compliance_configs.framework, compliance_rules.framework, and any UI enum you mirror.
  2. Seed the rules — INSERT INTO compliance_rules (framework, rule_id, name, description, category, severity, is_builtin) … ON CONFLICT (rule_id) DO NOTHING, following migration 003.
  3. Add evaluation logic — evaluateRule(rule, samples, configData, agentReachable) in src/compliance/service.js is a switch on rule.id. Add a case per rule returning { passed, details }. Include the connection status string in details, as the existing cases do — auditors need to know whether the agent actually responded.
  4. Add sample inputs to generateSamples(framework, agentInfo) so on-demand checks have something to exercise.
  5. Optional: skip steps 2–4 entirely by importing an OSCAL catalog instead. That path creates rules from NIST controls without code changes — though rules created that way have no bespoke evaluator and fall through to the generic handling.

Add an agent protocol#

Example to copy: the mcp branch of forwardToAgent in src/gateway/proxy.js.

  1. Extend the agents.protocol CHECK constraint (a2a, mcp, rest, grpc today).
  2. Add a branch in forwardToAgent(). Return { data, usage } — usage may be null, in which case tokens are estimated.
  3. Handle health checking in src/registry/health.js. The existing code special-cases MCP URLs (/sse, /mcp) and falls back to GET <origin>/health otherwise.
  4. If the protocol needs per-method governance the way MCP does, model it on src/gateway/mcp-proxy.js — a dedicated router with its own authentication and its own dispatch — rather than trying to generalise the REST path.

Add a middleware enforcement stage#

Copy the two-function shape used by every existing stage in src/gateway/middleware/index.js:

function myEnforcer(req, res, next) {
    // 1. Path gate
    if (!req.path.startsWith('/api/v1/gateway/') ||
        req.path === '/api/v1/gateway/policy/check') return next();

    // 2. Module toggle gate
    settingsService.getModuleStatus('my_module').then(enabled => {
        if (!enabled) return next();
        _myEnforcerCore(req, res, next);
    }).catch(() => next());        // fail-safe on flag lookup
}

function _myEnforcerCore(req, res, next) {
    tracer.startActiveSpan('agentshield.my.evaluate', async (span) => {
        try {
            const result = await myService.evaluate(/* … */);
            span.setAttribute('agentshield.my.decision', result.allowed ? 'allow' : 'deny');
            if (!result.allowed) {
                myDenialCounter.add(1, { reason: result.reason });
                await auditService.log({ traceId: req.traceId, eventType: 'my_enforcement',
                    actorId: req.user?.id, outcome: 'denied',
                    details: { reason: result.reason }, ipAddress: req.ip });
                span.end();
                return res.status(4xx).json({ success: false, error: '…',
                                              reason: result.reason, code: 'MY_DENIAL' });
            }
            req.myResult = result;
            span.end();
            next();
        } catch (err) {
            span.recordException(err);
            span.end();
            next(err);          // fail closed — or next() to fail open
        }
    });
}

Then export it, register it in src/index.js in the right position (order is the security model), define its counters near the top of the middleware file, and add a module definition to MODULE_DEFINITIONS in agentshield-dashboard/src/pages/Settings.jsx so it can be toggled.

Decide fail-open vs fail-closed explicitly. Policy and budget call next(err); guardrails and compliance call next(). Whichever you choose, put a comment saying why — the existing code does, and that comment is the only record of the decision.

Add a database migration#

  1. Create migrations/0NN_description.sql, numbered sequentially.
  2. Make it idempotent: CREATE TABLE IF NOT EXISTS, ADD COLUMN IF NOT EXISTS, ON CONFLICT … DO NOTHING. Migrations from 002 onward all follow this.
  3. It runs automatically on the next API boot.

Two cautions:

  • Migration failures are logged as non-fatal — the service starts anyway. Read the startup log after deploying schema changes; a silent failure looks like a working deploy.
  • There is no distributed lock. Start one instance before scaling out.

Add a console page#

  1. Create src/pages/MyModule.jsx.
  2. Register it in App.jsx — add to PAGES (key → { title, component }) and to the relevant NAV_ITEMS section. Add minRole if it should be role-gated.
  3. If it belongs to a toggleable module, add the mapping to MODULE_NAV_MAP so the page hides when the module is off.
  4. Add API methods to src/api.js — always go through the shared request() wrapper so you inherit token injection, silent refresh, and session-expiry handling.
  5. Style with the existing CSS variables in index.css (--bg-*, --text-*, --accent-*, --border-color). The theme is a hand-rolled design system, not a component library.

Add a new authentication method#

authenticate() in src/gateway/middleware/index.js tries API key, then JWT. To add a third (mTLS header, OIDC bearer, HMAC signature):

  1. Insert your branch before the JWT fallback, guarded by the presence of your header.
  2. Set req.user to the same identity shape everything downstream expects: { id, role, email, department, … } — the policy engine reads context.user, so any attribute you add here becomes available as a policy condition field.
  3. Set req.authMethod for audit attribution.
  4. Set the agentshield.auth.method, .success, .user_id, .role span attributes and increment authFailureCounter on failure, so observability stays uniform.
  5. Mirror it in mcpAuthenticate in src/gateway/mcp-proxy.js — the MCP path has its own copy of this logic and does not share the middleware.

Extension points that need no code#

Worth knowing before writing anything:

GoalMechanism
New access rules of arbitrary complexityRego policies — validated and compiled at save time
New compliance controlsOSCAL catalog import
New guardrail configurationsYAML import/export, versionable in git
New PII patternscustomPatterns in a pii_shield rule config
New injection signaturesextraPatterns in a prompt_injection rule config
New model pricingmodel_pricing rows via the Settings UI
Tuning evaluation scoringSettings → Evaluation (weights and latency tiers)
Phased rollout of enforcementSettings → Modules

Things to be careful about#

  1. Middleware order is the security model. Reordering src/index.js changes what is enforced before what. Budget after guardrails, for instance, means you pay for blocked requests.
  2. The MCP path duplicates governance logic. Policy, guardrail, and budget checks exist separately in mcp-proxy.js. A change to enforcement semantics must land in both places or the two paths diverge silently.
  3. JSONB columns have no schema validation. Malformed rule config surfaces as a runtime evaluator failure — and for guardrails, that means fail-open. Validate on write.
  4. pg returns BIGINT and NUMERIC as strings. Always parseInt/parseFloat before comparing, as cost/service.js does.
  5. In-process caches are per-instance. Module flags (30 s), model pricing (5 min), and evaluation settings are not shared across replicas. Don't build anything requiring immediate cluster-wide consistency on top of them.
  6. There is no automated test suite to catch you. npm test references a jest.config.js that does not exist in the repo. Adding tests alongside your change is the single highest-leverage contribution you can make.
