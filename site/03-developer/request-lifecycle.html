Request Lifecycle#

The exact path a request takes, in registration order, with failure semantics. This is the document to read before changing anything in src/gateway/.

Registration order#

From src/index.js:

app.use(helmet());
app.use(cors());
app.use(compression());
app.use(express.json({ limit: '10mb' }));
app.use(morgan('short', …));

app.use(traceId);            // 1
app.use(authenticate);       // 2
app.use(auditLogger);        // 3
app.use(policyEnforcer);     // 4
app.use(budgetChecker);      // 5
app.use(guardrailEnforcer);  // 6
app.use(complianceSampler);  // 7

The inline comments in the source number these 1, 2, 3, 4, 5, 5.5, 6 — an artefact of guardrailEnforcer being added after the others. The registration order above is what executes; treat the comment numbering as historical.

Routes are mounted after the chain:

Stage 1 — traceId#

Establishes correlation. Precedence:

  1. The active OpenTelemetry span's trace id, if one exists
  2. The X-Trace-Id request header
  3. A fresh UUID v4

Sets req.traceId, req.startTime, the X-Trace-Id response header, and — when a span is active — the agentshield.trace_id span attribute.

This id is stamped onto every audit record, cost record, and compliance sample for the request. Never blocks.

Stage 2 — authenticate#

Bypassed for: /api/v1/auth/login, /api/v1/auth/refresh, /api/v1/admin/invitations/accept, /api/v1/public/*, /health, /ready, and anything under /mcp/ (which authenticates inline).

Order of attempts

  1. X-API-Key present → SHA-256 the value, look up api_keys, check is_active and expires_at, update last_used_at fire-and-forget. Yields an identity of { id: owner_id ?? key_id, role, email: apikey-<prefix>@agentshield.local, department: 'api', apiKeyId, apiKeyName, scopes }.
  2. Otherwise Authorization: Bearer <jwt> → jwt.verify against JWT_SECRET. The decoded payload becomes req.user.

Sets req.authMethod to api_key or jwt.

Failure — 401 with AUTH_REQUIRED, INVALID_API_KEY, TOKEN_EXPIRED, or INVALID_TOKEN. Increments agentshield.auth.failures{method,reason}.

The dashboard's api.js reacts specifically to TOKEN_EXPIRED by refreshing once and retrying. Preserve that code on the server or silent refresh breaks.

Stage 3 — auditLogger#

Registers a res.on('finish') handler and calls next() immediately — the write happens after the response is sent, so audit never adds latency.

On finish:

  1. Compute latency; derive outcome — <400 → allowed, <500 → denied, else error
  2. Record agentshield.gateway.latency_ms and agentshield.requests.total, tagged with method, route, and status code
  3. Apply the noise filter, then write

Noise filter. Skipped only when the request is read-only (GET/HEAD/OPTIONS) and the path starts with one of:

/api/v1/settings/, /api/v1/audit, /api/v1/auth/, /api/v1/dashboard, /health, /favicon, or /api/v1/agents (GET-only list).

Mutations on these paths are always logged. /api/v1/audit is filtered to prevent audit reads generating audit records recursively.

The write is .catch(() => {}) — audit failure never affects the response.

Stage 4 — policyEnforcer#

Path gate — runs only when the path starts with /api/v1/gateway/, and never on /api/v1/gateway/policy/check.

Module gate — settingsService.getModuleStatus('policies'). Disabled → next() immediately. A failure reading the flag also calls next() (fail-safe toward availability).

Core — builds the evaluation context:

{
  user: req.user || {},
  agent: { slug, type, name, vendor },   // resolved from req.params.agentSlug
  workflow: {},                          // note: never populated — see caveat
  action: 'invoke',
  timestamp: <ISO>
}

Then policyService.evaluate(context):

  1. SELECT * FROM policies WHERE is_active AND policy_type='access_control' ORDER BY priority ASC
  2. Zero rows → allow ("No policies defined — default allow")
  3. For each policy in priority order: definitive allow or deny matches and returns; anything else falls through to the next policy. A Rego policy with no compiled WASM is warned about and skipped. resources (at least one must match, against workflow-or-agent), conditions (all must match, against the whole context). Conditions with an empty field are filtered out.
    • policy_format = 'rego' → instantiate the stored WASM, feed the input document. A
    • Otherwise → JSON evaluation: subjects (all must match, against context.user),
  4. No match → deny ("No matching policy — default deny")

On denial — write an audit record (policy_enforcement, outcome denied, with reason and policy), increment agentshield.policy.denials, return 403 POLICY_DENIED.

On engine error — next(err) → 500. Fails closed.

Metrics — agentshield.policy.decisions{decision,policy_name} and the agentshield.policy.evaluate_ms histogram on every evaluation.

⚠️ Caveat: workflow is initialised to null and never assigned in the middleware, so workflow-scoped policy conditions evaluate against an empty object. Policies targeting workflows by slug will not match on the workflow run path.

Stage 5 — budgetChecker#

Same path and module gates (cost_management).

Extracts the agent slug from the path (/api/v1/gateway/agents/<slug>/invoke) so agent-scoped budgets are considered, then costService.checkBudget(userId, teamId, departmentId, agentSlug):

  1. Build the scope list in order: user, team, department, agent, then always global
  2. For each scope, load active budgets whose period_start <= NOW()
  3. If a budget's period has expired → archive into budget_history, reset counters, skip it
  4. Compare current_tokens vs token_limit and current_cost_cents vs cost_limit_cents (both parsed with parseInt — PostgreSQL returns bigint/numeric as strings)
  5. Over limit and hard_limit → deny. Over limit without hard_limit → allow
  6. Over warn_threshold → log a warning (this feeds the alerts endpoint)

On denial — audit budget_enforcement, increment agentshield.budget.exceeded{scope, limit_type}, return 402 BUDGET_EXCEEDED with the scope and figures.

On engine error — 500. Fails closed.

Counters are incremented after the call completes, in costService.recordUsage, which updates every matching scope including agent budgets keyed by UUID or slug.

Stage 6 — guardrailEnforcer#

Same path and module gates (guardrails).

Requires req.params.agentSlug; without one it skips (so the workflow run path is not guardrail-screened at this stage).

guardrailsService.evaluateInput(agentSlug, req.body):

  1. Resolve the agent; no agent → allow
  2. Load active guardrail profiles assigned to it; none → allow
  3. Extract text from the payload; empty → allow
  4. For each profile, load enabled rules where scope = 'input' or 'both', ordered by sort_order
  5. Evaluate each rule by type. Block if and only if the profile's mode is block and the rule's severity is critical or high

Every violation — blocking or not — is written to audit as guardrail_violation with profile, rule, type, severity, and details, and added as a span event.

On block — 422 GUARDRAIL_VIOLATION with the full violation array.

On engine error — logged, then next(). Fails open, deliberately: *"don't block requests if guardrails service errors."* This is the single most important operational fact in the chain — alert on these errors.

Non-blocking results are attached as req.guardrailResult for downstream use.

Stage 7 — complianceSampler#

Same path and module gates (compliance).

Monkey-patches res.json to capture the response body, then calls next(). When the route handler eventually calls res.json(body):

  1. The original res.json runs — the client is served immediately
  2. An IIFE runs asynchronously: applicability (a config with assigned agents applies only to those; a config with none applies to all), then Math.random() < sample_rate detection over the combined text, insert with pii_detected, pii_types, and flagged
    • complianceService.shouldSample(agentId, workflowId) — for each active config, decide
    • On a hit, storeSample(): SHA-256 both bodies, AES-256-GCM encrypt both, run PII

Never blocks, never delays, never fails the request.

Route handler — REST invoke#

POST /api/v1/gateway/agents/:agentSlug/invoke

  1. Resolve the agent; is_active === false → 503; health_status === 'unhealthy' → 503
  2. forwardToAgent(agent, req.body, req.headers): errors become 502 with Content-Type: application/json, X-Forwarded-By: AgentShield, plus the agent's configured upstream credential (bearer token or custom api_key header)
    • protocol === 'mcp' → invokeMcpAgent() via the MCP SDK (SSE or Streamable HTTP);
    • otherwise → axios.post(endpoint_url, body, { timeout: 30_000, maxContentLength: 10 MB })
    • upstream 4xx/5xx → 502 with the status and body; unreachable → 503
  3. Cost metering — prefer the agent's usage block (input_tokens/prompt_tokens, output_tokens/completion_tokens, model, cost_cents); otherwise estimate at ceil(len/4) per side and mark the record estimated. Emits gen_ai.usage.* span attributes.
  4. Outbound DLP — extract data.reply ?? data.output ?? data.text; if it's a string, run complianceService.redactPII() and replace the value in both the top-level reply and the nested field
  5. Respond { success, data, reply, meta: { traceId, agentSlug, latencyMs, usage, dlp } }

Route handler — workflow run#

POST /api/v1/gateway/workflows/:workflowSlug/run

Resolve workflow → refuse if is_enabled === false (503) → refuse if no steps (400). Then, for each step in order, inside its own agentshield.workflow.step span:

  • Resolve the agent. Inactive and is_optional → record skipped, continue. Inactive and required → 503, whole run fails.
  • Forward, meter cost (with workflowId attached), and set currentInput = response.data for the next step.

Returns the final output plus a per-step latency summary under one trace id.

Path-specific gaps: no guardrail screening (no agentSlug param), no outbound DLP, and data_flow_rules is not applied — output is passed through whole.

MCP proxy path#

POST /mcp/:agentSlug bypasses the global authenticator and runs mcpAuthenticate (API key, then Bearer), returning JSON-RPC errors rather than REST envelopes.

  1. Validate the JSON-RPC 2.0 envelope → -32600 if malformed
  2. Resolve the agent → -32002 if missing, not protocol: mcp, inactive, or unhealthy
  3. Dispatch by method: capabilities then forward
    • no id (notification) → 202, no upstream call
    • ping → answered locally
    • initialize → intercepted; AgentShield merges its own server info with upstream
    • tools/call → policy (-32003) → guardrails (-32004) → budget (-32005),
    • tools/list and anything else → forwarded unfiltered
  4. Audit as mcp:tools/call:<toolName> or mcp:<method>
  5. Cost: for tools/call, estimate tokens from the serialized params and result (costCents: 0, estimated: true)

GET /mcp/:agentSlug serves the SSE stream; DELETE ends the session.

Error handling#

errorHandler is the final middleware:

{ success: false, error: <message>, code: <err.code ?? 'INTERNAL_ERROR'>, traceId }

err.statusCode sets the status (default 500). The message is exposed only when err.isOperational is true — AppError instances — otherwise it is replaced with "Internal server error". The exception is recorded on the active span and logged with the trace id and stack.

Unmatched routes return 404 with the requested path.

Fail-open vs fail-closed — the summary table#

Three consequences worth internalising:

  1. A disabled module provides zero enforcement — it is bypassed, not made permissive.
  2. A failing guardrail engine is silently permissive. Monitor Guardrail enforcement error log lines, not just HTTP status codes.
  3. Policy and budget faults surface as 500s. That is intentional: never admit a request whose access or spend could not be verified.
