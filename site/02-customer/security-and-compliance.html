Security & Compliance Posture#

What the platform enforces, how, and — equally important — where the boundaries are. Written so a security reviewer can assess it without reading the source.

Authentication#

ControlImplementation
Password storagebcrypt, cost factor 10
Access tokensJWT (HS256), default 15-minute lifetime
Refresh tokensJWT, default 7 days, exchanged at /auth/refresh
Session trackinguser_sessions rows; admins can list and revoke per session or all sessions for a user
Brute-force defence5 consecutive failures → 30-minute account lock, recorded in login_history
Failed-login forensicsEvery attempt logged with outcome (success/failed/locked), IP, user agent, and reason
Account stateDeactivated accounts are refused with a distinct message from bad credentials
Service credentialsAPI keys: 24 random bytes hex-encoded with an ask_ prefix, stored as SHA-256 only, with role, scopes, optional expiry, and last-used tracking

Known limitations

  • No MFA/TOTP, no SSO/OIDC/SAML. Identity is local to the deployment.
  • JWTs are stateless: revoking a session row does not invalidate an already-issued access token before its 15-minute expiry.
  • The dashboard stores tokens in localStorage, which is XSS-reachable by design.
  • Password complexity is not enforced server-side.

Authorization#

Role hierarchy — numeric levels, "this level or above":

RoleLevelTypical scope
super_admin4Everything, including Settings
admin3User management, budgets, API keys, destructive deletes
editor2Author policies, guardrails, workflows, run checks
viewer1Read-only

Roughly 70 routes carry an explicit requireRole guard; the remainder require only valid authentication. Notably, read access to governance configuration is not role-restricted — any authenticated principal can list policies, guardrail profiles, budgets, audit records, and compliance samples metadata. Treat "authenticated" as "trusted reader" and use API-key scoping to constrain machine callers.

Resource-level authorization (which caller may invoke which agent) is the job of the policy engine, not the role system.

The enforcement chain#

Ordered as registered in src/index.js:

#StageBlocks withOn engine error
1Trace id assignment——
2Authentication401500
3Audit hook registration—never fails the request
4Policy enforcement403 POLICY_DENIEDfails closed (500)

6Guardrail enforcement422 GUARDRAIL_VIOLATIONfails open (request proceeds)

The fail-open behaviour of guardrails is a deliberate availability trade-off, and it has a security consequence: if the guardrail service is erroring, traffic flows unscreened while the platform still reports healthy. Alert on guardrail error logs specifically.

The same three controls (policy, guardrails, budget) are applied to MCP tools/call in the MCP proxy, in that order.

Data protection#

At rest#

DataProtection
Compliance samples (request/response bodies)AES-256-GCM, key derived via scrypt from COMPLIANCE_ENCRYPTION_KEY; random IV and auth tag stored with the ciphertext
Sample integritySHA-256 of the plaintext stored alongside, so tampering is detectable without decryption
Passwordsbcrypt
API keysSHA-256 (irreversible; the raw key exists only in the creation response)
Everything else (policies, agents, audit, cost)Plaintext in PostgreSQL — rely on database-level encryption at rest

Key management caution. COMPLIANCE_ENCRYPTION_KEY is a single static value with no rotation mechanism. Changing it renders every previously stored sample undecryptable. Store it in a managed secret store (the GCP scripts use Secret Manager) and treat it as permanent for the life of your retention window.

In transit#

TLS is expected to terminate in front of the service (Cloud Run provides it in the reference deployment); the Node process itself serves plain HTTP. Upstream agent connections use whatever scheme the registered endpoint URL specifies — register https:// endpoints.

Inbound detection#

pii_shield guardrails detect SSN, credit card, email, phone, DOB, and MRN patterns in request payloads, plus any custom regexes you supply. Detection can block (severity critical/high in a block profile) or record.

Outbound redaction (DLP)#

On POST /gateway/agents/:slug/invoke, the agent's textual reply is rewritten before it reaches the caller: SSN, credit card, email, phone, MRN, DOB, and IP address are replaced with [REDACTED:TYPE]. Applied actions are reported in meta.dlp.outbound and on the trace span.

Scope limit. Outbound redaction runs on the single-agent REST invoke path only — not on workflow steps and not on MCP tools/call results. If a strict egress boundary is required, route sensitive traffic through single-agent invokes, or add guardrail rules with scope: output.

Audit & non-repudiation#

  • audit_log is append-only enforced by PostgreSQL — CREATE RULE … DO INSTEAD NOTHING on UPDATE and DELETE. An attacker with database write access cannot quietly rewrite history through normal SQL; they would have to drop the rules, which is itself a schema-level event.
  • Records capture trace id, event type, actor id and type, resource, action, outcome, JSONB details, source IP, and latency.
  • Governance decisions are logged with their reasons: policy denials carry the matched policy; guardrail violations carry every triggered rule with type and severity; budget denials carry the scope and figures.
  • Audit writes are fire-and-forget so governance can never take down the data path. The trade-off: under database stress, records can be dropped.
  • Read-only polling traffic is filtered out of the trail by design; mutations always land.

Compliance frameworks#

Built-in rule sets — 5 rules each for SOX, HIPAA, GDPR, PCI-DSS, and 3 for custom — covering data integrity, segregation of duties, PHI/PII detection, encryption adequacy, access control, minimum-necessary, retention, consent, erasure, cross-border transfer, cardholder-data detection, and audit completeness.

Rules are editable in the console. Built-ins can be disabled but not deleted; custom rules can be added freely.

NIST OSCAL — import a catalog (validate → preview → select control groups → import as rules, tagged with oscal_control_id); export a completed check as an OSCAL Assessment Result for a GRC platform.

Default retention is 2190 days ≈ 6 years, matching HIPAA. Configurable per compliance config.

How to read a compliance check. Rule evaluation is pattern-based. Some rules assert a platform-provided control and pass unconditionally (e.g. "Access Logging Completeness" — true because audit middleware exists). Others are regexes over request/response text. This is legitimate control attestation with supporting evidence; it is not behavioural verification of the agent. Present it that way to auditors and it holds up. Present it as proof the agent never mishandled data and it will not.

Retention is a configured value, not an enforced one — nothing in the code purges samples when retention_days elapses. Implement deletion in your database maintenance if your policy requires it.

Attention items

  1. CORS is fully open. Any origin can call the API with a valid credential.
  2. Default credentials are published. admin@agentshield.local / admin123 is seeded by migration 001 and appears in both repos' READMEs. Rotate at install time.
  3. Regex-based content inspection. Guardrails cannot catch semantically-equivalent attacks; obfuscated or paraphrased injection passes. The llm_judge rule type exists but is skipped in real-time enforcement.
  4. Order-of-list dependence in policy. First match wins, so a broad allow at a low priority number will shadow narrower rules behind it. Review priority ordering as a security artefact.
  5. The proxy is only a boundary for traffic that goes through it. Nothing prevents a client from calling a registered agent's endpoint URL directly. Enforce network-level restrictions so agents accept connections only from AgentShield.
