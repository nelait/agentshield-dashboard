Redis is declared in config, Compose, and the GCP infrastructure script, and the ioredis / rate-limit-redis packages are installed — but the application code does not currently open a Redis connection. It is provisioned capacity for distributed rate limiting, not an active dependency. You can omit it for a single-instance deployment.

Local — Docker Compose#

docker-compose.yaml defines three services:

docker compose up -d
docker compose logs -f api

The Compose file mounts migrations/001_initial_schema.sql into the Postgres init directory; the remaining migrations are applied by the API at boot.

Dashboard separately:

cd agentshield-dashboard && npm install && npm run dev   # http://localhost:5173

Container image#

FROM node:20-alpine
# installs OPA v1.4.2 static binary → required for Rego compilation
WORKDIR /app
COPY package*.json ./
RUN npm ci --production
COPY . .
EXPOSE 3000
CMD ["node", "src/index.js"]

Two things to know:

  1. OPA is baked in. Rego policy authoring does not work without the opa binary on PATH. If you build your own image, keep that step.
  2. .dockerignore deliberately keeps docs/product/ while excluding the rest of docs/ — the documentation portal serves those Markdown files from disk at runtime. Removing them breaks the portal.

GCP — the scripted path#

Ten numbered scripts under deploy/gcp/, roughly 30 minutes end to end.

cd deploy/gcp
cp config.env.template config.env      # set your project id (config.env is gitignored)
chmod +x *.sh

./01-setup-project.sh     # create project, enable APIs             ~1 min
./02-create-infra.sh      # Cloud SQL, Memorystore, VPC connector  ~10 min
./03-create-secrets.sh    # Secret Manager entries                  ~1 min
./04-deploy-backend.sh    # build + deploy to Cloud Run             ~5 min
./05-deploy-dashboard.sh  # build with VITE_API_BASE, Firebase      ~3 min
./06-deploy-agents.sh     # four demo agents                        ~5 min
./07-register-agents.sh   # register them in the registry           ~1 min
./08-run-tests.sh         # POC validation                          ~2 min

./10-setup-domain.sh      # optional: custom domain → Cloud Run     ~2 min
./09-teardown.sh          # destroys everything (confirmation required)

DashboardFirebase Hosting, SPA rewrites to /index.html

Demo agents deployed by 06: echo-agent (REST — policy/auth/audit baseline), finance-agent (REST — cost and budget), support-agent (REST — guardrails), weather-mcp (MCP — protocol and workflow chaining).

Documented cost: ≈ $95/month — Cloud Run ≈ $30, Cloud SQL ≈ $30, Memorystore ≈ $35, Firebase Hosting $0, Secret Manager ≈ $0.10. Dropping Memorystore while it is unused takes this to roughly $60.

AWS / Azure#

deploy/aws/ and deploy/azure/ contain README placeholders only — no scripts. The container has no GCP-specific dependencies, so ECS/Fargate + RDS, or Container Apps + Azure Database for PostgreSQL, are straightforward ports. Budget the work: it is not scripted today.

Production hardening checklist#

Ordered by consequence.

Before any real traffic

  • Change ADMIN_PASSWORD and reset the seeded admin@agentshield.local password
  • Set a strong JWT_SECRET (it signs both API and doc-portal tokens)
  • Set a real 32-byte COMPLIANCE_ENCRYPTION_KEY and store it where it can be recovered — losing it makes every stored compliance sample unreadable
  • Set DB_PASSWORD; enable DB_SSL / sslmode=require
  • Terminate TLS in front of the service
  • Constrain CORS — cors() is currently mounted with no origin allow-list, so any origin may call the API with a valid credential
  • Decide the module posture (Settings → Modules) and confirm Policies is on

Operational readiness

  • Point OTEL_EXPORTER_OTLP_ENDPOINT at a real collector
  • Wire /health (deep, includes DB) and /ready (shallow) to your orchestrator
  • Alert on agentshield.policy.denials, agentshield.budget.exceeded, agentshield.auth.failures
  • Alert on guardrail-service errors — guardrails fail open, so an error stream means you are unprotected while looking healthy
  • Back up PostgreSQL; audit_log and compliance_samples are the irreplaceable tables
  • Plan retention/partitioning for audit_log and cost_records — they grow per request and nothing prunes them today

Scale considerations

  • Migrations run at boot with no distributed lock — start one instance first, then scale
  • Module-toggle and pricing caches are per-process; toggles converge across instances within ~30 s
  • The demo-request and doc-access rate limiters are in-process Maps, so limits are per-instance, not global
